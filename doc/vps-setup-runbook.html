Standing up LMMS on a rented VPS

Everything from the order form to the moment UAT users get the URL. The order matters: the box is locked down before the stack goes on it, the data is loaded before it faces the internet, and HTTPS is in place before a single real member record is reachable. Your existing deploy/setup-test-server.ps1 already does most of the middle — the work is retargeting it off the E: drive and the LAN IP it was written for.

Approved at VALUE — 2 vCPU / 2 GB / 50 GB

2 GB is workable for UAT, provided nothing heavy ever runs on the box. Steady-state LMMS is one Node process, nginx and PostgreSQL serving a handful of testers, and that fits. What does not fit is the setup work: the Informix data load and the frontend build are each far hungrier than anything UAT will ask of the server afterwards, and they are where the 8 GB test box already fell over — the CachedPlan out-of-memory that forced MIGRATE_BATCH to 100, and the commit-limit crash loop (error 1455).

So this runbook moves both off the VPS. The data is loaded on your dev machine and shipped as a database dump (phase 6), and both halves are built locally and shipped as dist folders (phases 4–5). Neither is a workaround — deploy-test.ps1 already builds locally for exactly this reason. With those two off the box, the memory ceiling stops being what decides whether this works.

The escape hatch: upgrading to PRO is in-place and prorated, so trying VALUE first costs setup time, not money. Phase 10 sets a tripwire that tells you with measurements, rather than argument, whether to go back to management for the extra RM29 a month.

First hour: lock the box down

45 min · before installing anything

199.1.1.32 sat behind the company firewall. This one does not. An unhardened Windows box with 3389 open to the world starts collecting brute-force attempts within minutes of coming up.

03

Install the two things the script cannot

30 min

setup-test-server.ps1 installs Node, Git, NSSM and PM2 for you via winget. It only checks for PostgreSQL and nginx, and refuses to run without them.

postgresql.conf on a 2 GB box

The stock config is wrong for this machine in both directions — too little cache, too much room for per-connection growth. Set:

shared_buffers = 256MB              # up from 128MB; not the 512MB you would use on 4GB
work_mem = 4MB                      # leave it - this one multiplies per sort, per connection
max_connections = 25                # down from 100; each backend costs memory
max_parallel_workers_per_gather = 0
plan_cache_mode = force_custom_plan

force_custom_plan is the targeted fix for the CachedPlan out-of-memory. Under the default auto, the server switches to a cached generic plan after about five executions of the same statement and accumulates memory across the session — which is exactly why that failure struck partway through a refresh rather than on the first batch. Forcing a custom plan each time costs a little planning CPU and removes the accumulation entirely.

05

Run the provisioning script

40 min · over RDP, PowerShell as Administrator

Seven phases, all automated: database and role, extract, .env, npm install, Prisma migrate and seed, both builds, nginx as an NSSM service, PM2 registered for auto-start. It finishes with four HTTP checks.

Set-ExecutionPolicy Bypass -Scope Process -Force
.\setup-test-server.ps1
Known defect — verify this by hand afterwards

Phase 3 of the script rewrites credentials into ecosystem.config.js using -replace 'postgresql://lhb_app:CHANGE_ME@'. That placeholder is no longer in the file. The committed value now reads postgresql://lhb_app:Lhb@8899@127.0.0.1:5432/lhb_mms, so the replace matches nothing and silently leaves the old test-server password behind.

The backend still starts, because index.ts loads the root .env with override: true and that file is written correctly. But a wrong credential sitting in a committed file is a landmine for whoever next runs PM2 without a .env present — which is exactly how the test server is configured today. Open ecosystem.config.js after the run and set DATABASE_URL and JWT_SECRET by hand.

Edit the script before you run it on 2 GB

Phase 5 of setup-test-server.ps1 runs npm run build for the backend and the frontend on the server, and Phase 4 runs npm install in frontend/ to make that possible. On 2 GB that is the most likely place for the whole run to die — and it is pure waste, because you already built both in phase 4.

Comment out the frontend npm install and both npm run build blocks, but keep the two Test-Path assertions so the script still fails loudly if a dist folder is missing from the zip. Keep npm install at the root and in backend/ — the backend's runtime dependencies and the Prisma client are still needed. Use --omit=dev there to halve the work.

06

Load the data — on your machine, not the VPS

2–4 hours, almost all of it on the dev box

The Informix load is the heaviest thing this system ever does: roughly 1.2 million rows through Node and Prisma, with several importers holding an entire file in memory because the collapse logic needs it. It is what broke an 8 GB machine. Do not run it on 2 GB — load it where you have RAM and ship the finished database.

A pg_restore is also far cheaper than the migration that produced it: it streams COPY, with no Node process, no thousand-parameter createMany, and none of the plan-cache accumulation that causes the CachedPlan failure. That is why this route works on a small box.

# ── on your DEV machine, against a LOCAL postgres ──────────────────
$env:DATABASE_URL  = "postgresql://postgres:PASSWORD@localhost:5432/lhb_mms"
$env:MIGRATE_BATCH = "100"
npx prisma migrate deploy
npm run prisma:seed
.\refresh-test-db.ps1 -DryRun      # parses every file, writes nothing
.\refresh-test-db.ps1
pg_dump.exe -U postgres -F c -f lhb_mms_seed.dump lhb_mms

# ── on the VPS, after copying the dump up ──────────────────────────
psql.exe  -U postgres -c "DROP DATABASE lhb_mms;"
psql.exe  -U postgres -c "CREATE DATABASE lhb_mms OWNER lhb_app;"
pg_restore.exe -U postgres -d lhb_mms --no-owner lhb_mms_seed.dump
This becomes the standing refresh procedure

Every future UAT data refresh follows the same route: re-export from Informix, load on the dev machine, dump, restore. refresh-test-db.ps1 keeps working exactly as written — you are just pointing it at a different DATABASE_URL. Copy the migrate\ folder to the VPS anyway, including the committed *_unload.sql scripts, so the box carries its own provenance.

Do not skip — verify the row counts

Importers warn per bad row and carry on, so a run prints "migration complete" over a table that loaded nothing. On 27 August this happened twice at once: ps_seasondate.txt gained a leading ps_cocode column and CpSeasonDate came back 0 of 424, taking the whole CP season grading with it; lvc_master.txt introduced status C and LvcCode loaded 11 of 22.

Count every migrated table and compare against CLAUDE.md. Treat anything that returns zero or comes back sharply short as a layout change until proven otherwise.

07

Wire your dev machine to the new host

20 min

WinRM over HTTP on 5985 is fine inside an office. Exposed to the internet it is an authentication endpoint anyone can reach, so it gets the same treatment as RDP.

08

HTTPS and credential hygiene

1 hour · before any real member data is reachable

32,387 members' personal data behind a session cookie over plain HTTP was acceptable on the company LAN. On a public host it is not — and the proposal's own risk table committed you to mitigating third-party hosting of PII.

Repository hygiene — fix at the source

backend/ecosystem.config.js:30 is committed to git carrying a live database password (Lhb@8899). The JWT_SECRET on the line below it is still a placeholder, which is the correct pattern — the password should match it.

Restore the CHANGE_ME placeholder in the tracked file and keep real values only in the untracked .env. That fixes two things at once: the credential stops travelling with the repo and the deploy zip, and the setup script's -replace from phase 5 starts matching again. If this repository has ever been pushed anywhere off your machine, treat that password as burned and rotate it on the test server too.

09

Backups — a condition of the approval

45 min, plus a restore test

The proposal's risk table made nightly off-site database backups a condition of both hosting options. This is the phase that discharges that commitment, and the one most likely to get deferred.

# Task Scheduler, nightly, running as a service account
pg_dump.exe -U postgres -F c -f D:\backups\lhb_mms_%DATE%.dump lhb_mms
