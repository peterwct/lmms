The order you actually type things in, from a freshly provisioned Windows box to staff logging in. Each stage is tagged with where you run it — on the VPS, on your dev machine, or on the existing test server — because this procedure moves between all three. Substitute the four placeholders in the table below and the commands are copy-pasteable as written.

Two decisions that make this shorter than the runbook

1. Do not run deploy/setup-test-server.ps1 on this box. It hardcodes the E: drive, it runs both builds on the server (the likeliest thing to exhaust 2 GB), it has a credential-rewrite defect that silently leaves the old test-server password in place, and its migrate deploy + seed steps are pointless when you are restoring a database anyway. Stages 2–7 below do the same work by hand, in a form you can watch succeed one step at a time.

2. Copy the test server's database — do not re-import from Informix. This is not just faster, it is the only correct option: months of staff CRUD edits exist nowhere else. The resort active/inactive split is 12/312 because staff retired resorts through fn 2; a fresh resort_mast load would hand you 49/275. The same is true of the LVC retirements, the MAR flags, the RCI corrections and every department and report grant. Stage 5 does it with pg_dump/pg_restore.

Three unrelated layers of credential — don't let them blur

1. Windows Administrator gets you into the machine over RDP. Already changed.

2. PostgreSQL roles — postgres and lhb_app above. These exist inside PostgreSQL and have no connection to any Windows account. Two of them rather than one is least privilege: the backend is a long-running process facing the network, so if a bug or a leaked config file exposes its credential, the damage is bounded by DML on one database instead of the whole instance. It also mirrors the test server, which is what lets deploy-test.ps1 work against this box unchanged — it swaps in a postgres URL for migrate deploy, then re-grants lhb_app.

3. LMMS logins — your own username, jennifer, admin and the rest. They live in the User table as bcrypt hashes and arrive with the database restore in stage 5, so there is nothing to set up. JWT_SECRET is a fourth secret but not a password: it is the key the backend signs session cookies with, which is why rotating it (9e) logs everyone out and belongs before UAT starts rather than during.

Harden the box

30 min

On the VPS, over RDP

This machine is on the public internet, unlike 199.1.1.32. You have already done the first and most important part — the rest takes twenty minutes and is much harder to retrofit once the app is running.

Connecting — set drive redirection before you log in

Win+R → mstsc. Computer <VPS_IP>, username <VPS_IP>\Administrator — qualifying it matters on a workgroup machine, the same reason deploy-test.ps1 uses 199.1.1.32\Administrator. The certificate warning on first connect is expected on a fresh box.

In Show Options → Local Resources → More…, tick your local drive. This cannot be turned on mid-session, and stages 3–5 depend on it — it is how the deploy zip and the database dump reach the VPS, arriving under \\tsclient\. Then save the whole thing as an .rdp file from the General tab.

Connect from the office for this stage: step 1b whitelists wherever you happen to be connected from, so doing it from home would lock the office out.

  2. This is the one command that can lock you out

    You are connected over RDP as you run it. A wrong address drops your session and you cannot reconnect. Before you start, find the VNC / console option in the Shinjiru control panel — that is your way back in. If Shinjiru offers a firewall in their own panel, do this there instead: it sits in front of the VM, so a mistake never costs you OS access.

    Is your office IP static? Many business lines here are not. If the ISP rotates it overnight you arrive locked out, so allow the surrounding range instead — looser, but it survives rotation.

Get-NetFirewallRule -DisplayGroup "Remote Desktop" | Get-NetFirewallAddressFilter

02

Install the stack

40 min, mostly downloads

On the VPS

Install PostgreSQL to C:\PostgreSQL18 rather than accepting the installer's C:\Program Files\PostgreSQL\18. It keeps every path in the repo's scripts one drive letter away from correct instead of a different shape, and it keeps the space out of your command lines.

  2. The settings go at the end of C:\PostgreSQL18\data\postgresql.conf. The file uses the last occurrence of any setting, so adding them at the bottom beats hunting for five values that sit commented out higher up.

    Type the settings into Notepad — never through a PowerShell command

    Every scripted way of writing this file — a here-string piped to Add-Content, an array passed to -Value — ends up pasted into the config instead of run, and PostgreSQL then refuses to start with syntax error … near token naming "$", "Copy-Item", "@", or the quoted settings themselves. That happened three times on this build. The commands below deliberately contain none of the settings.

    1. Back the file up and open it — in PowerShell:

    Copy-Item 'C:\PostgreSQL18\data\postgresql.conf' 'C:\PostgreSQL18\data\postgresql.conf.bak' -Force
notepad C:\PostgreSQL18\data\postgresql.conf

    2. In the Notepad window: press Ctrl+End — the cursor lands just after # Add settings for extensions here — press Enter once, then type these five lines and Ctrl+S.

    Type into Notepad. The end of C:\PostgreSQL18\data\postgresql.conf
    shared_buffers = 256MB
work_mem = 4MB
max_connections = 25
max_parallel_workers_per_gather = 0
plan_cache_mode = force_custom_plan

    Nothing else goes in — no $, no quotes, no brackets, no Add-Content.

    3. Restart and verify — in PowerShell. A config file is never "run"; PostgreSQL reads it at startup, so the restart is what applies it.

    Restart-Service postgresql-x64-18
Get-Service postgresql-x64-18

& 'C:\PostgreSQL18\bin\psql.exe' -U postgres -c "SELECT name, setting, unit FROM pg_settings WHERE name IN ('shared_buffers','work_mem','max_connections','max_parallel_workers_per_gather','plan_cache_mode');"

    Expect shared_buffers 32768 (unit 8kB, i.e. 256MB), max_connections 25, plan_cache_mode force_custom_plan. Finding the first two also set near lines 65 and 132 is normal — those are the installer's, and the last occurrence wins.

    If it will not start

    PostgreSQL dies before its log collector starts, so the reason is in the Windows event log, not C:\PostgreSQL18\data\log\. The message names the offending line number, which is usually enough to see what strayed into the file:

    Get-WinEvent -LogName Application -MaxEvents 15 |
  Where-Object { $_.ProviderName -match 'postgres' } |
  Select-Object TimeCreated, Message | Format-List

    To get back to a known-good file, restore the step 1 backup and begin again:

    Copy-Item 'C:\PostgreSQL18\data\postgresql.conf.bak' 'C:\PostgreSQL18\data\postgresql.conf' -Force
Start-Service postgresql-x64-18

    If it says could not map anonymous shared memory, shared_buffers is more than this box will reserve — edit that one line to 128MB and leave the other four.

    This whole step is optional — skip it if it fights you

    The reason for plan_cache_mode = force_custom_plan was the CachedPlan out-of-memory during the Informix migration scripts — and this box never runs them. Stage 5 restores a pg_dump, which streams COPY and never touches that code path. The stock config carries UAT perfectly well. Restore the backup, start the service, go on to 2c, and revisit the tuning later once you can see real memory behaviour on the box.

    Why force_custom_plan

    It is the targeted fix for the CachedPlan out-of-memory. Under the default auto, the server switches to a cached generic plan after about five executions of the same statement and accumulates memory across the session — which is exactly why that failure struck partway through a refresh rather than on the first batch. Forcing a custom plan each time costs a little planning CPU and removes the accumulation.

    Why the temp folder and the flatten

    The zip contains a top-level nginx-x.xx.x\ folder, so extracting straight into C:\Apps\nginx leaves you with C:\Apps\nginx\nginx-1.28.0\nginx.exe — one level too deep, and nothing downstream finds it. Step 1f already created C:\Apps\nginx as an empty folder, which makes the nesting easy to miss.

    Don't start it yet. It has no config and nothing to serve — step 6a copies your nginx.conf in and 6b registers it as a service through NSSM.

05

Copy the database across

1–2 hours, mostly transfer

Test server, then the VPS

This carries the schema, the migration history, all the Informix data and every staff edit made in UAT — departments, users, report grants, resort statuses, MAR flags, LVC retirements, RCI corrections. Re-importing from the exports would silently discard all of it.

Run pg_dump ON the test server, not from your desk

Your dev machine has PostgreSQL 16; the test server runs 18. A version-16 pg_dump refuses to dump from a version-18 server outright, so pointing it at 199.1.1.32 will simply fail. Take the dump over RDP with the test server's own binaries at E:\PostgreSQL18\bin\, which is also why stage 2 insisted the VPS gets 18 as well.

  1. & 'E:\PostgreSQL18\bin\pg_dump.exe' -U postgres -F c -Z 6 `
     -f E:\lhb_mms_20260917.dump lhb_mms
Get-Item E:\lhb_mms_20260917.dump | Select-Object Length, LastWriteTime
  2. & 'E:\PostgreSQL18\bin\psql.exe' -U postgres -d lhb_mms -A -F "," -o E:\counts_source.csv -c @"
SELECT table_name,
       (xpath('/row/c/text()',
              query_to_xml(format('SELECT count(*) AS c FROM %I.%I','public',table_name),
                           false, true, '')))[1]::text::bigint AS rows
FROM information_schema.tables
WHERE table_schema='public' AND table_type='BASE TABLE'
ORDER BY table_name;
