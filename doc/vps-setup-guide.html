Setting up LMMS on the new VPS

The order you actually type things in, from a freshly provisioned Windows box to staff logging in. Each stage is tagged with where you run it — on the VPS, on your dev machine, or on the existing staging server — because this procedure moves between all three. Substitute the four placeholders in the table below and the commands are copy-pasteable as written.

Which box is which

The VPS is the TEST server — mms.leisureholidays.com.my, where UAT happens. 199.1.1.32 is the STAGING server, on the office LAN. There is no production server yet; Phase 2 decides that at go-live.

This document was written while 199.1.1.32 was still called "the test server", and was renamed throughout on 24 Sep. Script and file names were deliberately left alone — deploy-test.ps1, refresh-test-db.ps1, setup-test-server.ps1 and the lhb_restoretest scratch database all still say "test", and renaming those would break working tooling for a wording change.

Data flows staging → VPS. The Informix importers must never run on the 2 GB VPS, so a refresh is loaded on staging, verified there, then shipped up with pg_dump/pg_restore — stage 5 below, scripted as sync-vps-db.ps1. The nightly VPS → staging pull (stage 9) runs the other way and is a backup, not a refresh path.

Two decisions that make this shorter than the runbook

1. Do not run deploy/setup-test-server.ps1 on this box. It hardcodes the E: drive, it runs both builds on the server (the likeliest thing to exhaust 2 GB), it has a credential-rewrite defect that silently leaves the old test-server password in place, and its migrate deploy + seed steps are pointless when you are restoring a database anyway. Stages 2–7 below do the same work by hand, in a form you can watch succeed one step at a time.

2. Copy the staging server's database — do not re-import from Informix. This is not just faster, it is the only correct option: months of staff CRUD edits exist nowhere else. The resort active/inactive split is 12/312 because staff retired resorts through fn 2; a fresh resort_mast load would hand you 49/275. The same is true of the LVC retirements, the MAR flags, the RCI corrections and every department and report grant. Stage 5 does it with pg_dump/pg_restore.

Three unrelated layers of credential — don't let them blur

1. Windows Administrator gets you into the machine over RDP. Already changed.

2. PostgreSQL roles — postgres and lhb_app above. These exist inside PostgreSQL and have no connection to any Windows account. Two of them rather than one is least privilege: the backend is a long-running process facing the network, so if a bug or a leaked config file exposes its credential, the damage is bounded by DML on one database instead of the whole instance. It also mirrors the staging server, which is what lets deploy-test.ps1 work against this box unchanged — it swaps in a postgres URL for migrate deploy, then re-grants lhb_app.

3. LMMS logins — your own username, jennifer, admin and the rest. They live in the User table as bcrypt hashes and arrive with the database restore in stage 5, so there is nothing to set up. JWT_SECRET is a fourth secret but not a password: it is the key the backend signs session cookies with, which is why rotating it (9e) logs everyone out and belongs before UAT starts rather than during.

On the VPS, over RDP

This machine is on the public internet, unlike 199.1.1.32. You have already done the first and most important part — the rest takes twenty minutes and is much harder to retrofit once the app is running.

Connecting — set drive redirection before you log in

Win+R → mstsc. Computer <VPS_IP>, username <VPS_IP>\Administrator — qualifying it matters on a workgroup machine, the same reason deploy-test.ps1 uses 199.1.1.32\Administrator. The certificate warning on first connect is expected on a fresh box.

02

Install the stack

40 min, mostly downloads

On the VPS

Install PostgreSQL to C:\PostgreSQL18 rather than accepting the installer's C:\Program Files\PostgreSQL\18. It keeps every path in the repo's scripts one drive letter away from correct instead of a different shape, and it keeps the space out of your command lines.

  2. The settings go at the end of C:\PostgreSQL18\data\postgresql.conf. The file uses the last occurrence of any setting, so adding them at the bottom beats hunting for five values that sit commented out higher up.

    Type the settings into Notepad — never through a PowerShell command

    Every scripted way of writing this file — a here-string piped to Add-Content, an array passed to -Value — ends up pasted into the config instead of run, and PostgreSQL then refuses to start with syntax error … near token naming "$", "Copy-Item", "@", or the quoted settings themselves. That happened three times on this build. The commands below deliberately contain none of the settings.

    1. Back the file up and open it — in PowerShell:

    Copy-Item 'C:\PostgreSQL18\data\postgresql.conf' 'C:\PostgreSQL18\data\postgresql.conf.bak' -Force
notepad C:\PostgreSQL18\data\postgresql.conf

    2. In the Notepad window: press Ctrl+End — the cursor lands just after # Add settings for extensions here — press Enter once, then type these five lines and Ctrl+S.

    Type into Notepad. The end of C:\PostgreSQL18\data\postgresql.conf
    shared_buffers = 256MB
work_mem = 4MB
max_connections = 25
max_parallel_workers_per_gather = 0
plan_cache_mode = force_custom_plan

    Nothing else goes in — no $, no quotes, no brackets, no Add-Content.

    3. Restart and verify — in PowerShell. A config file is never "run"; PostgreSQL reads it at startup, so the restart is what applies it.

    Restart-Service postgresql-x64-18
Get-Service postgresql-x64-18

& 'C:\PostgreSQL18\bin\psql.exe' -U postgres -c "SELECT name, setting, unit FROM pg_settings WHERE name IN ('shared_buffers','work_mem','max_connections','max_parallel_workers_per_gather','plan_cache_mode');"

    Expect shared_buffers 32768 (unit 8kB, i.e. 256MB), max_connections 25, plan_cache_mode force_custom_plan. Finding the first two also set near lines 65 and 132 is normal — those are the installer's, and the last occurrence wins.

    If it will not start

    PostgreSQL dies before its log collector starts, so the reason is in the Windows event log, not C:\PostgreSQL18\data\log\. The message names the offending line number, which is usually enough to see what strayed into the file:

    Get-WinEvent -LogName Application -MaxEvents 15 |
  Where-Object { $_.ProviderName -match 'postgres' } |
  Select-Object TimeCreated, Message | Format-List

    To get back to a known-good file, restore the step 1 backup and begin again:

    Copy-Item 'C:\PostgreSQL18\data\postgresql.conf.bak' 'C:\PostgreSQL18\data\postgresql.conf' -Force
Start-Service postgresql-x64-18

    If it says could not map anonymous shared memory, shared_buffers is more than this box will reserve — edit that one line to 128MB and leave the other four.

    This whole step is optional — skip it if it fights you

    The reason for plan_cache_mode = force_custom_plan was the CachedPlan out-of-memory during the Informix migration scripts — and this box never runs them. Stage 5 restores a pg_dump, which streams COPY and never touches that code path. The stock config carries UAT perfectly well. Restore the backup, start the service, go on to 2c, and revisit the tuning later once you can see real memory behaviour on the box.

    Why force_custom_plan

    It is the targeted fix for the CachedPlan out-of-memory. Under the default auto, the server switches to a cached generic plan after about five executions of the same statement and accumulates memory across the session — which is exactly why that failure struck partway through a refresh rather than on the first batch. Forcing a custom plan each time costs a little planning CPU and removes the accumulation.

    The zip contains a top-level nginx-x.xx.x\ folder, so extracting straight into C:\Apps\nginx leaves you with C:\Apps\nginx\nginx-1.28.0\nginx.exe — one level too deep, and nothing downstream finds it. Step 1f already created C:\Apps\nginx as an empty folder, which makes the nesting easy to miss.

    Don't start it yet. It has no config and nothing to serve — step 6a copies your nginx.conf in and 6b registers it as a service through NSSM.

Before UAT users touch it: HTTPS and backups

2 hours

On the VPS

32,387 members' personal data behind a session cookie over plain HTTP was acceptable on the company LAN. On a public host it is not — and the approved proposal's own risk table committed you to nightly off-site backups either way.

function Write-Log($status) {
    # 2026-09-22, 02:30:14 - 02:31:02  OK - lhb_mms_20260922-0130.dump
    "{0} - {1}  {2}" -f $stamp, (Get-Date).ToString('HH:mm:ss'), $status |
      Add-Content -Path $Log -Encoding ASCII
}

try {
    $cred = Import-Clixml 'C:\Scripts\vps-cred.xml'
    $s = New-PSSession -ComputerName $VpsHost -Credential $cred
    try {
        $latest = Invoke-Command -Session $s {
            (Get-ChildItem C:\backups\lhb_mms_*.dump |
             Sort-Object LastWriteTime -Descending | Select-Object -First 1).FullName
        }
        if (-not $latest) { throw "No dump found on the VPS" }

        $name   = Split-Path $latest -Leaf
        $target = Join-Path $Dest $name
        if (-not (Test-Path $target)) {
            Copy-Item -FromSession $s -Path $latest -Destination $target
        }

        # prove the transfer - a truncated file exists, looks plausible,
        # and restores to nothing
        $remote = Invoke-Command -Session $s -ArgumentList $latest `
                    -ScriptBlock { param($p) (Get-FileHash $p -Algorithm SHA256).Hash }
        $local  = (Get-FileHash $target -Algorithm SHA256).Hash
        if ($remote -ne $local) { Remove-Item $target -Force; throw "Hash mismatch on $name" }

        # Two EMPTY files hash identically, so the check above would pass a
        # 0-byte dump straight through. Size is what catches that.
        $size = (Get-Item $target).Length

            Remove-Item $target -Force
            throw "Pulled dump is only $size bytes - check the VPS backup job"
        }

        $cfg = Join-Path $Dest 'config'

                       'C:\Apps\nginx\conf\nginx.conf') {
            Copy-Item -FromSession $s -Path $f -Destination $cfg -Force
        }
    }
    finally { Remove-PSSession $s -ErrorAction SilentlyContinue }

    $all  = Get-ChildItem $Dest -Filter 'lhb_mms_*.dump' | Sort-Object LastWriteTime -Descending
    $keep = [System.Collections.Generic.HashSet[string]]::new()
    $all | Select-Object -First 14 | ForEach-Object { [void]$keep.Add($_.FullName) }
    $all | Group-Object { Get-Date $_.LastWriteTime -UFormat %Y-%V } |
      Select-Object -First 8 | ForEach-Object {
        [void]$keep.Add(($_.Group | Sort-Object LastWriteTime -Descending |
                          Select-Object -First 1).FullName) }
    $all | Where-Object { -not $keep.Contains($_.FullName) } | Remove-Item -Force

    Write-Log "OK - $name"
}

    02:30 on an always-on server, and what that costs

    The VPS dumps at 01:30, so an 02:30 pull collects that night's file. A desktop would have forced a daytime schedule just to be sure the machine was awake; the staging server removes that compromise. The price is that the task needs Run whether user is logged on or not, and therefore a stored Windows password — so changing the staging server's Administrator password breaks this task, silently. Put it on whatever checklist covers password rotation. If Register-ScheduledTask is awkward about the password, create the task in the Task Scheduler GUI and tick that box; same result.

    Watch the disk — E: is shared with the staging server's own data. E:\PostgreSQL18 and E:\Apps\lhb-mms sit on the same volume, so a backup folder left to grow would take the UAT database down with it. The retention prune bounds it at roughly 22 files (14 daily plus 8 weekly), but check free space after the first fortnight, once you know the real dump size rather than an estimate of it.

    Phase 2 may retire this machine. If the staging server goes at go-live the backup destination goes with it — name that in the decision rather than discovering it afterwards.

    PowerShell eats double quotes bound for a native exe

    LMMS table names are PascalCase, so SQL requires "Member" in double quotes — and PowerShell 5.1 strips those when handing an argument to psql.exe. The query arrives as bare Member, PostgreSQL folds it to lowercase, and you get ERROR: relation "member" does not exist.

    The query above sidesteps it entirely by containing no double quotes. When you do need them in a one-off, escape each with a backslash — that is how PowerShell 5.1 passes a literal quote through:

    & $psql -U postgres -d lhb_restoretest -t -A -c 'SELECT count(*) FROM \"Member\";'
    Differences in that diff are expected, not failures

So Member, Agreement, AuditLog and RciEnrolment should read equal or slightly higher, and _prisma_migrations identical at 67.

    What actually indicates a bad restore: any table at 0 that was not 0 in the baseline, a table that shrank (nothing in UAT deletes wholesale), or a table name missing entirely.

what is what, and what breaks when it changes

Two machines each run their own PostgreSQL, and both instances have a role called postgres and a role called lhb_app. Same names, different servers, different passwords, no relationship whatsoever. That single fact is behind most of the confusion here — a password that authenticates perfectly on one box is simply wrong on the other, and the error it produces says only "password authentication failed", never "wrong server".

The mix-up to expect

Putting the lhb_app password where postgres belongs produces FATAL: password authentication failed for user "postgres" — which reads like a broken script rather than a transposed credential. The one-line test that settles it:

$env:PGPASSWORD = '<the password you are unsure about>'
& 'C:\PostgreSQL18\bin\psql.exe' -U postgres -c "SELECT current_user;"
& 'C:\PostgreSQL18\bin\psql.exe' -U lhb_app -d lhb_mms -c "SELECT current_user;"
Remove-Item Env:\PGPASSWORD

Whichever prints a role name is the account that password belongs to. Clear PGPASSWORD between tests — a stale value left in the shell makes the next attempt fail for the previous reason, which is its own hour of confusion.
